## Evidence method

The review used READMEs, package manifests, Python command/agent/protocol declarations, API routes, client screens and API clients, service implementation files, Go route registrations and runtime loaders, tests, and the existing migration decisions. The per-repository sections link their source entry points; individual features link target implementations or the decision explaining their absence.

The ledger is a capability inventory, not a symbol-by-symbol port list. CRUD variants and related command actions are grouped when they share an implementation and migration gate. Alternative providers, background agents, deliberate cuts, legacy prototypes and external integrations stay separate. Private credentials, datasets, generated dependencies and Git history contents were not copied.

## Evidence precedence

1. Current implementation and call wiring establish whether a path exists or is a stub.
2. Later explicit decisions override older plans.
3. Existing contract reports establish historical compatibility for their covered shapes.
4. Unit/integration test source shows intended checks, not a newly observed pass.
5. README descriptions and design-only statements identify candidates, not proof of completion.

Examples of reconciled differences: the root README still describes absent Pi installer/provisioning/package support that now has code; the original PLAN mentions fastText, later cut in CC D9; Forge test-install was initially cut, then restored in code; camera list routes exist while streaming remains unavailable. See [Orchestration](Get-Orchestration-Features.md) and [Nodes](Get-Nodes-Features.md).
